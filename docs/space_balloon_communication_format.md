# PLANET-Q共通通信フォーマット

- 可変長なデータをやり取りしたい
- 通信の堅牢性を高めたい
- 設計変更が容易にできるような柔軟性がほしい

上記の要望を満たすためにBluetoothなどで使われているTLV方式(Tag-Length-Value)を参考にしてプロトコルを策定した。

## プロトコル構造

まずTLVの構造について解説する。

- タグ(Tag)       1バイト   このデータが何を表すのか事前に変数名と0-255の値を対応させておくことで表す
- 長さ(Length)    1バイト   データがn (0 <= n <= 253) バイトあることを表す
- データ(Value)   nバイト

Value の中の複数バイトの値（i16, u32, i32 など）はリトルエンディアン（下位バイトが先）で並べる。
TagとLengthは1バイトなのでバイト順の影響を受けない。
なお、フレーム末尾のCRCは上位バイトが先である。

ペイロードは最大255バイトで、そこにTagとLengthの2バイトも入るので、1つのTLVのValueは最大253バイトになる。

このTLV形式のデータを直接つなげて以下のようなペイロードを作る

[TLVデータ, TLVデータ, TLVデータ, ...]

このペイロードに宛先や送信元、チェックサムを追加して以下のような構造となる

[0x7E, (宛先ID), (送信元ID), (ペイロード長(バイト数で)), ペイロード, CRCチェックサム(上位バイト), CRCチェックサム(下位バイト), 0x7F]

## CRC

- 方式は CRC-16/CCITT-FALSE（多項式 0x1021、初期値 0xFFFF、反転なし、最後のXORなし）
- 計算する範囲は、スタッフィングする前の「宛先ID・送信元ID・ペイロード長・ペイロード」
- `"123456789"` の CRC は `0x29B1` になる

## スタッフィング

先頭の0x7Eと最後の0x7Fはデータの始まりと終わりを示すものであるから、0x7Eと0x7Fの間（宛先IDからCRCまで）に区切りと同じバイトが出てきたときはスタッフィングする

- 0x7E -> 0x7D 0x81
- 0x7F -> 0x7D 0x80
- 0x7D -> 0x7D 0x7D

に変換

CRCはスタッフィングする前のバイトで計算し、計算したCRCもスタッフィングの対象になる。

## 例

宛先ID 0x10、送信元ID 0x01、ペイロード `01 02` のフレーム

```text
7E 10 01 02 01 02 1E F1 7F
```

`1E F1` は `10 01 02 01 02` の CRC。
